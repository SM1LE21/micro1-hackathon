# AMBIGUITIES

Each problem-statement ambiguity: both readings, the reading we chose, and why. The PDF names "incomplete requirements" as part of the point — documented interpretation is scored behaviour. Slice: ADR 0002 (GDPR Art. 30 inventory + erasure-path check).

| # | Ambiguity | Reading A | Reading B | Chosen | Why |
|---|---|---|---|---|---|
| 1 | What counts as personal data | Only directly identifying fields (name, email, phone, IP) | Any field on a table linked to a data subject, incl. timestamps, preferences, free text, JSON blobs | B, with a category label per field (identifier · contact · financial · behavioural · free-text-may-contain · technical) | Art. 4(1) says "any information relating to an identifiable natural person". A undercounts. Tables with no link to a subject (`Product`) are out. |
| 2 | "Erasure propagates" to a store | A deletion primitive for that store is called somewhere in the codebase | A static call path exists from the erasure entry point to that primitive | B | A is what the drifted hand-written document claims. B is what happens when a user closes their account. |
| 3 | Erasure entry point | Discovered by the agent (`delete_user`, `close_account`, a DELETE route, a management command) | Declared per repo by the human | A, human confirms at the gate; manifests declare it for scoring | Real repos do not label it. Declaring it by hand would remove the part of the task the baseline gets wrong. |
| 4 | Soft delete | Counts as erasure if the app stops serving the row | Does not count; the data persists | B. Verdict "erased after N days" only if a scheduled purge job with a path to a hard delete exists, timer cited | Art. 17 is about the data, not its visibility. |
| 5 | Anonymisation | Not erasure | Erasure if every personal-data field on the path is overwritten irreversibly | B, split in two: `anonymised` (constant or non-reversible overwrite, no surviving key to the subject) reaches erasure; `pseudonymised` (hash, token, UUID, mask, or a surviving foreign key) does not and is a false safe when claimed | WP29 Opinion 05/2014: "the processing must be irreversible"; EDPB 2026 erasure report found controllers substituting "basic pseudonymisation or partial masking" for deletion. Sources in docs/research/gdpr-sources.md §3.2. Amended 2026-08-28 after research. |
| 6 | Backups and logs | In scope as stores for both inventory and erasure verdict | Out of scope entirely | In scope for the inventory; backup stores render `governed_by_retention` (schedule found in code, cited) or `no_schedule_evidenced` instead of an erasure verdict; both count as not reaching erasure in the scored tuple | ICO "beyond use" guidance and the EDPB 2026 report both govern backups by retention schedule and procedure; the EDPB found controllers claiming schedules they did not have, so the absence is a finding. Sources in docs/research/gdpr-sources.md §3.1. Amended 2026-08-28. |
| 7 | Third-party recipients | Any outbound SDK import (Stripe, mail, analytics, error tracking) is a recipient | Only where a personal-data field flows into the call | B, with A as the discovery heuristic | Art. 30(1)(d) recipients are those who receive the data; an import alone is not evidence. External stores need a deletion call on the path or are flagged `external — manual erasure required`. |
| 8 | Legal cells (purpose, legal basis, risk class) | Agent infers them from code ("marketing mail → consent") | Agent never fills them | B. A suggestion may appear in a marked column; the cell renders "requires human completion" | Ground rule 05. A wrong legal basis is the most harmful sentence this tool could write. |
| 9 | Primary metric | Inventory F1 only | Erasure-verdict accuracy only | F1 over `(store, field, reaches-erasure)` tuples; false-safe count as a separate must-be-zero row | One metric is required. A tuple is only right if the field and its fate are both right, which is what the founder signs. Fine-grained verdict labels are reported, not scored. |
| 10 | A "case" | One repository | One (repository, store) pair | A; per-store results appear as sub-rows | A judge's mental model of a case is one execution. |
| 11 | Baseline resources | One prompt over a tree dump, no tools | Same tools, same instructions, no verifier or gate | B | A is a straw man. The only difference between arms must be the design choice under test. Verifier tool calls count as steps in the advanced arm and are reported. |
| 12 | Ground truth for real repos | Taken from the verifier's own output | Hand-labelled under a written protocol before the agent runs | B | A would make the metric measure the verifier, not the agent. |
| 13 | Django `on_delete=CASCADE` | Counts as a propagation path for the related table | Only explicit delete calls count | A for relational rows; `FileField`/`ImageField` need an explicit storage delete (`post_delete` handler or on the path) | That is how Django behaves: rows cascade, files survive. |
| 14 | Unresolvable call (dynamic dispatch, decorator magic, missing import) | Assume it reaches | Assume it does not | Neither: verdict `unverified`, listed separately, counted as not-reaching for the false-safe row | Guessing in either direction is the failure the tool exists to prevent. |
| 15 | Django admin `delete` on the user model | Counts as an erasure entry point when the admin is enabled for that model | Only application code counts | A, flagged `admin_only` in the artifact | Operators do delete users through the admin; the cascade and signal path it triggers is real code. The flag lets a lawyer see that no self-service path exists. |
| 16 | Retention granularity | One time limit per store | One per category of data where the code distinguishes them | B | CNIL: where categories are not subject to the same retention periods, the different periods must appear in the record (gdpr-sources.md §6.3). A `users` table purged at 30 days except an invoice reference kept ten years is two rows. |
