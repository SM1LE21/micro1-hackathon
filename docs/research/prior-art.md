# Prior art — what already scans code for personal data, and what none of it does

status: research only, 2026-08-28

This file answers the two questions a judge asks in the first minute: *doesn't Bearer/Privado/OneTrust already do this?* and *why an LLM at all?* Every tool below was checked against its own documentation or its own source on 2026-08-28, not from memory. Where a claim is an absence ("no tool does X"), the search that produced the absence is written down so someone can repeat it.

## 0. How this was checked

Release and archive dates come from the GitHub REST API rather than a rendered page. Three of the "nobody does this" claims are measurements, and all three are re-runnable:

- Bearer's documentation sitemap has 876 URLs: 373 third-party *recipes*, 473 security *rules*, the two section index pages, and 28 everything else. Grepping the whole sitemap for `delet|eras|reten` returns zero URLs [S8]. Fetching those 28 pages and grepping the rendered text (21,535 words, navigation chrome included) for `delet|erasur|retention` returns zero hits [S8b]. The URL sweep alone would only show that no page is *slugged* for deletion, which is a weaker claim than the one this file makes.
- Privado's own full documentation export (`llms-full.txt`, 123,915 bytes) contains the string `delete` five times: once inside an AWS S3 sink regex, four times in Privado's own website privacy policy. `erasure` and `retention` appear zero times anywhere in the file. Re-run: `curl -s https://docs.privado.ai/llms-full.txt | awk 'BEGIN{IGNORECASE=1}{n=gsub(/delete/,"delete"); if(n)print NR": "n}'` returns `620: 1`, `1535: 2`, `1554: 1`, `1566: 1` [S13].
- The public Semgrep registry returns 305 rulesets. Zero of them mention `privacy`, `PII`, `GDPR` or `personal data` anywhere in name, description, tags, categories or language list [S23].

Two fetches failed and were routed around:

- FETCH FAILED: https://www.usenix.org/conference/usenixsecurity20/presentation/andow (HTTP 403). The abstract was taken from the USENIX-hosted camera-ready PDF instead [S28].
- FETCH FAILED: https://ethyca.com/docs/dev-docs/datasets and three sibling doc URLs (Next.js shell, no article body). Fides behaviour below is quoted from the Fides source instead [S17], which is stronger evidence anyway.

Assumption: a tool's public documentation is a fair statement of what its open-source build does. Where a vendor's marketing page and its docs disagree, the docs win, and the disagreement is noted.

## 1. Bearer CLI

**URL** github.com/Bearer/bearer · docs.bearer.com
**Licence** Elastic License 2.0 (the GitHub API reports `NOASSERTION`; the repository's `LICENSE.txt` opens with the words "Elastic License 2.0") [S1]
**Latest release** v2.1.1, published 2026-08-24T09:59:06Z. Last commit to `main` 2026-08-24. Not archived [S2]
**Languages (OSS build)** Java, Python, Ruby, JavaScript/TypeScript, PHP, Go. C#, Kotlin, Elixir, VB.Net, Rust and Swift are Pro-only [S4]
**Status after Cycode** Cycode announced the acquisition on 2024-03-05, in a release headed "Press Releases | March 5, 2024" [S9b], and closed it on 2024-04-30. The completion release reads: "Cycode, the leader in Application Security Posture Management (ASPM), has finalized its acquisition of Bearer, an AI-powered SAST and API discovery company." The CLI was kept open under the "Cygives" free-tools initiative [S9]. It is alive: more than two years after the acquisition it is still shipping patch releases [S2].

This is the closest thing that exists, and it is worth being precise about the overlap.

**(i) Personal-data discovery.** Yes, and this is its best feature. Bearer classifies against 122 data types [S6] using a two-stage heuristic on names, not values: "it discovers and classifies data by identifying patterns in the source code… it never views the actual values—but only the code itself" [S5]. The clever part is the known/unknown object split. A class called `User` is a "Known Object" that Bearer has pre-identified as corresponding to an individual, so its `id`/`name`/`email` attributes are classified aggressively. A class called `Foo` gets a conservative pattern set first, and only after something like `first_name` matches does Bearer "assume that this object represents an individual" and apply an extended set to the rest [S5].

**Python support: yes, in the OSS build, with Django named as the supported framework** [S4]. Cross-file analysis is a Pro feature. The supported-languages legend defines the third column as "Advanced interprocedural and inter-file analysis capabilities (Pro only)", and the column is orthogonal to the other two: Ruby, JavaScript/TypeScript and PHP carry OSS and Pro ticks with no cross-file tick, while C# has no OSS tick and does have a cross-file one [S4]. The README splits it the same way, listing seven OSS languages and then, under **Bearer Pro by Cycode**, "**Advanced Cross-file Analysis**: Java • Python • C# • Go" [S1]. So a Bearer OSS scan of a Django repo classifies within a file and does not follow a call across files, which is the analysis an erasure path needs.

**(ii) Erasure paths.** No. There is no deletion, erasure or retention concept in any of the 28 substantive documentation pages, and no rule or recipe URL mentions one [S8][S8b]. Bearer answers "where does personal data go", never "does it come back out".

**(iii) Self-verification.** No claim-level verification. Bearer is a rule engine, so its output is its rules' output; there is no second pass that can reject a finding.

**(iv) Record of processing.** Explicitly not the record, but the input to one. Bearer's strongest version of the claim is in the privacy guide, which lists "Create a record of processing activities (ROPA) for GDPR" as a use case and says the report "allows you to collect information (sensitive data, data subjects, internal and third-party components processing sensitive data) that are required to comply with numerous privacy laws" [S7]. The README is more careful: "Records of Processing Activities (RoPA) input for GDPR compliance reporting" [S1]. The privacy report is a CSV of two arrays. `Subjects` rows look like `{"subject_name": "User", "name": "Telephone Number", "detection_count": 14, …}`; `ThirdParty` rows look like `{"third_party": "Sentry", "subject_name": "User", "data_types": ["Email Address"], …}` [S3]. Those are counts and names. There is no store, no `file:line` in the privacy report (the security and data-flow reports carry lines; the privacy report carries detection counts), no retention timer, no erasure verdict. A founder cannot hand that to a lawyer.

## 2. Privado

**URL** github.com/Privado-Inc/privado · docs.privado.ai
**Licence** LGPL-3.0 per the GitHub API; the repository page also lists GPL-3.0 [S15]
**Latest release** v1.3.91, published 2025-11-10T08:11:31Z. Last push to `main` the same day: **nine and a half months of no commits** as of today. Not archived [S15]
**Languages** The README says "We support Java and Python in GA" [S10]. The hosted docs still say "We support Java in GA and Python in alpha" [S11]. Assumption: Python is somewhere between alpha and GA and should not be assumed production-grade.
**Inputs/outputs** `privado scan <dir>` → `<dir>/.privado/privado.json`, five sections plus repository metadata [S12]

**(i) Discovery.** Yes: "It detects more than 110 personal data elements being processed" [S10].

**(ii) Erasure paths.** No, and the way it is absent is instructive. Privado's sink taxonomy is `third_parties`, `leakages`, `storages`, `internal_apis`, `miscellaneous` [S12a]. Its S3 sink rule matches `abortMultipartUpload|completeMultipartUpload|copy|create|delete|put|uploadPart` [S13], so a call to `s3.delete_object` is scored as *evidence that personal data reached S3*. That is the exact inverse of what an erasure check needs. Deletion is a data-flow edge to Privado, not a remedy.

**(iii) Self-verification.** No. The static engine emits flows; `violations` are separate rule hits with a `policyType` that is "either threat or compliance" [S12b].

**(iv) Record of processing.** This is the one tool that claims Art. 30 output, with two caveats that matter. First, it is not in the OSS scanner: "Our free cloud platform can be used to generate RoPA reports for one or more synced repositories" [S10]. The CLI produces `privado.json`; the record is produced after you sync results to Privado Cloud. Second, the generation is an unverified LLM: Privado's own post says "the Privado engineering team fine tuned a large language model (LLM) specifically to solve this problem. This LLM can identify all processing activities from Privado code scans and write detailed descriptions of how data is used for each activity" [S14]. The post describes no check on that output. That is exactly the arm this project uses as its **baseline**.

**What Privado gets right and we copy.** Its flow output carries a `paths` array where each step is `{sample, lineNumber, columnNumber, fileName, excerpt}` [S12a]. Evidence at the step level, not the finding level. That is the shape our erasure table needs.

## 3. Fides (Ethyca)

**URL** github.com/ethyca/fides
**Licence** Apache-2.0 (fideslang, the taxonomy, is CC-BY-4.0) [S16]
**Latest release** 2.86.2, 2026-06-01. Last push 2026-08-06.
**Archived by the owner today, 2026-08-28.** The repository banner reads: "This repository was archived by the owner on Aug 28, 2026. It is now read-only." [S16] The commercial product continues: Ethyca's own site, fetched the same day, leads with "Latest Aug 04, 2026 — Announcing Astralis: governing data at machine speed" and "Today we’re launching Astralis, the first tool that can do this at enterprise scale in the AI era" [S36]. The open-source repo does not. Anyone citing Fides as live prior art after today is citing a read-only repository.
**Languages** Python 3.13, Docker; integrations rather than language analysis [S18]

Fides is the only tool here that actually erases anything, and it is worth understanding why that does not compete with us. Fides does not read your code. It reads a *declaration* of your data. The header of `fides/api/graph/config.py` says so plainly:

> These objects correspond to the structure of the configurations that will form nodes from dataset and collection representations. … Schema == Dataset: any abstract data source that may contain multiple data sets. Table == Collection: a set of identifiable fields (e.g. rows of data). Field == Field: a single field in a collection, addressable by name. [S17]

A human writes a YAML dataset annotating each field with a FidesLang data category, marks which fields are identities ("Field identities are pointers to seed values. They indicate that this field can be populated with seed values, and so are eligible as traversal start nodes" [S17]), and Fides builds a graph over those declarations and executes access and erasure requests against the configured integrations. `uv run fides deploy up` then lets you run a real DSR against real databases in about five minutes [S18].

**(i) Discovery:** from declarations and connector schemas, not from application code. **(ii) Erasure:** yes. It *performs* erasure, the strongest capability in this list. **(iii) Verification:** it verifies the graph is traversable (`UnreachableNodesError`, `UnreachableEdgesError` are first-class exceptions [S17]) but it never checks the declaration against the code. If your dataset YAML omits the S3 bucket, Fides deletes everything it was told about and reports success. **(iv) Record:** data mapping is a listed feature, built from the same declarations.

The gap between Fides and this project is one sentence: **Fides trusts the annotation; the whole point here is that the annotation drifts from the code.** They compose rather than compete: the natural downstream of our record is a Fides dataset with the missing store in it.

## 4. Commercial data-mapping suites (OneTrust, Transcend, Osano, DataGrail)

None of the four describes source-code analysis anywhere in its own account of how discovery works; three of them name a different non-code mechanism instead, and the fourth names none. OneTrust defines the job as "the process of identifying and connecting data flows between systems" and says of its own product only that "OneTrust automates data mapping to identify, document, and maintain records of processing activities across systems" [S19]. How the inventory gets populated is not stated on that page. Transcend's System Discovery "leverages pre-built plugins to scan, discover, and automatically catalog all data systems" [S20]. DataGrail runs three mechanisms and names them: SSO/SAML detection ("DataGrail integrates with popular SAML/SSO providers (i.e. Okta, Entra ID, Google Apps) to identify third-party systems"), manual entry, and a containerised API agent that crawls the systems themselves [S21]. Osano is the same shape: "By integrating with your SSO provider and using a library of pre-built connectors, Osano auto-discovers systems and classifies personal data across structured and unstructured sources", and it then generates the RoPA from that inventory [S22]. The unit of discovery for all four is a **system you already pay for**: a SaaS vendor, a database, an identity provider. A `notes` column on your own `SupportTicket` table, an S3 prefix your own upload handler writes to, or a `cleanup_user_files()` that nothing calls are invisible to every one of them, because none of those is a system with a connector. They are complementary to this project at the boundary, not overlapping: they map your vendors, we map your repository.

## 5. Generic static analysis: Semgrep, CodeQL, and the published big-tech approaches

**Semgrep.** There is no privacy or PII ruleset in the public registry. All 305 published rulesets were pulled and searched; zero mention privacy, PII, GDPR or personal data in any field [S23]. Semgrep can obviously express a personal-data rule, and anyone can write one, but nobody has published one to the public registry. That absence is itself the finding.

**CodeQL** has a first-class notion of sensitive data, and it is a security notion, not a privacy one. The shared heuristics file states its scope in the header: "'Sensitive' data in general is anything that should not be sent around in unencrypted form" [S25]. The taxonomy is five strings (`secret`, `id`, `password`, `certificate`, `private`) where `private` is described as "private data such as credit card numbers", and identification is regex over identifier names (`maybePrivate()` matches `social.?security|employer.?identification|national.?insurance|resident.?id|passport.?(num|no)|([_-]|\b)ssn([_-]|\b)|…`) [S25]. The queries built on it are leak queries: `py/clear-text-logging-sensitive-data`, CWE-312/359/532, "If sensitive data is written to a log entry it could be exposed to an attacker who gains access to the logs" [S24]. A `full_name` column sitting correctly in Postgres is not a CodeQL finding, and should not be. It *is* an Art. 30 row. The two tools answer different questions with overlapping vocabulary, which is precisely why "just use CodeQL" is the wrong answer.

**Published internal approaches.** Meta's is the substantial one. Privacy Aware Infrastructure "offers efficient and reliable first-class privacy constructs embedded in Meta infrastructure", with Policy Zones as an information-flow-control layer that "controls not only data access but also how data is processed and transferred in real-time"; developers attach data annotations to assets and the runtime propagates and checks them across function calls and batch jobs [S26]. That is annotation-plus-runtime-enforcement at exabyte scale, and it presupposes an infrastructure that a five-person SaaS does not have. Google's published material on deletion is about Google's own pipeline, not about your code: a four-stage deletion pipeline with a soft-delete grace period and a commitment to delete "within a maximum period of about six months (180 days)" [S27]. Useful as a model of what a defensible deletion story sounds like; not a tool. No public write-up was found of a big-tech system that verifies an erasure entry point reaches every store by static analysis of application code.

## 7. Does anything generate an Art. 30 record from source code?

Art. 30(1) requires, among other things, "a description of the categories of data subjects and of the categories of personal data", "the categories of recipients to whom the personal data have been or will be disclosed", and, the row this project is built around, "where possible, the envisaged time limits for erasure of the different categories of data" [S34].

**One tool claims it: Privado, in its cloud platform, via a fine-tuned LLM, with no described verification step** [S10][S14]. Bearer produces "input" for a RoPA and says so [S1]. The four commercial suites build their inventory from connectors, SSO and containerised agents rather than from code, and generate the RoPA from that inventory [S19][S20][S21][S22]. Nothing in the academic set produces a record at all; the closest, GDPR-Bench-Android, localises violations against article text [S32].

Searches run, all on 2026-08-28, all returning nothing further: `generate "Article 30" "record of processing activities" automatically from source code tool open source`; `Privado open source "RoPA" record of processing activities generate from code repository`; `arXiv static analysis "right to erasure" OR "right to be forgotten" deletion completeness code GDPR paper`; `arXiv 2025 LLM GDPR compliance source code static analysis personal data detection`. Plus the three sitemap/registry sweeps in §0.

**Nothing found produces an erasure-path table from application source: per store, reaches or does not reach, with the call path cited `file:line`.** That is the empty square.

## Differentiation

Erasure reachability is the property nobody models: Bearer's documentation contains no deletion concept at all, in URLs or in page text [S8][S8b], Privado scores `s3.delete_object` as evidence that data *arrived* [S13], and so "does closing an account reach this bucket" cannot be expressed in either tool's output schema. The record of processing is the output here rather than raw material someone else assembles into one, which is the difference between Bearer's own word "input" [S1] and a table a founder signs. Every claim is re-verified by deterministic code the model cannot talk its way past, and an unresolvable call-graph edge renders `unverified` instead of a guess in either direction, where the one comparable Art. 30-from-code generator is a fine-tuned LLM writing activity descriptions with no described check [S14]. That same open-loop design is the baseline arm, so the changelog answers "what does the verifier buy over a good prompt" with a number rather than an argument.

The omissions are larger than the additions. Bearer covers six languages in its OSS build and twelve in Pro [S4]; this covers Python, and only Django and SQLAlchemy idioms, with everything else reported "unscanned". Bearer and Privado do interprocedural taint analysis with variable reconciliation and heuristics tuned on tens of thousands of open-source samples [S5], against a name-based intra-repo call graph here that will miss dynamic dispatch and decorator magic by construction. Fides deletes data for real [S18]; this tool never touches the target repository, never opens a PR, and never fixes the missing `storage.delete` it reports. The eval is 14 repositories, not 13,796 apps [S28].

## What we borrow

1. **Bearer's known-object / unknown-object split** [S5]. Classify aggressively on a class the tool already believes is a data subject (`User`, `Customer`, `Patient`); fall back to a conservative pattern set on an unknown class and only escalate once one attribute lands. This is the mechanism for AMBIGUITIES row 1 ("any field on a table linked to a data subject") and for the `products` negative in eval case S07: a table with no link to a subject stays out, and predicting it costs precision.
2. **Bearer's recipe registry as data, not code** [S3][S8]. 373 third-party service definitions live as files, and contributing one is a documented workflow. Our recipient SDK list (Stripe, Sentry, mail, analytics) and our store-kind and deletion-primitive rules ship the same way: rule sets as data, so adding a store kind is a data change, not a verifier change.
3. **Privado's sink taxonomy and step-level evidence** [S12a]. `third_parties` / `leakages` / `storages` / `internal_apis` maps almost one-to-one onto the store kinds in `evals/CASES.md`, and its `paths[].path[]` of `{fileName, lineNumber, excerpt}` is the right granularity: cite the step, not the finding. Our erasure evidence column follows it.
4. **Fides's identity-seeded traversal** [S17]. Fides marks which fields are identities and treats those as the only legal start nodes for a graph walk. Our verifier does the structurally identical thing with erasure entry points: the walk starts at `close_account`/`delete_user`/the admin delete, not anywhere a deletion primitive happens to appear. Where Fides errors with `UnreachableNodesError`, we render `not_erased`.
5. **CodeQL's classification enum, inverted** [S25]. Five fixed strings (`secret`, `id`, `password`, `certificate`, `private`) beat free-text labels for machine comparison, which is why our six categories (`identifier · contact · financial · behavioural · free_text_may_contain · technical`) are also a closed set. We keep the closed-set discipline and drop the security framing: CodeQL asks what must not leak, we ask what belongs to a person.
6. **GDPR-Bench-Android's multi-paradigm arms** [S32]. It benchmarks LLMs, a formal AST method, RAG and a ReAct agent on the same annotated set and reports that no paradigm wins everywhere. That is the argument for our arm design — same cases, same tools, same instructions, one variable — and its result (Formal-AST at 1.86%, LLMs far higher) is the reason the deterministic verifier is a *gate on* the model rather than a replacement for it.

## Honest weaknesses vs prior art

- **Bearer's classifier is better than ours will be.** Its heuristics were "built by analyzing tens of thousands of pieces of training sets from open-source projects, as well as Bearer's design partners" [S5], and it ships 122 curated data types [S6]. We have an LLM, six categories and 14 eval repositories. On the inventory half alone, run head-to-head on a Python/Django repo, Bearer should be expected to win on recall. Our claim is about the erasure half and about verification, and the README should say so before a judge tries it.
- **Privado already puts an Art. 30 report in front of users, today, at zero cost** [S10]. "Nobody generates the record from code" is only true if you add "with verification, and outside a cloud upload". That qualifier has to be stated in the demo, not buried.
- **The deterministic-verifier bet has a published counterexample.** GDPR-Bench-Android's Formal-AST baseline scored 1.86% line-level Accuracy@1 against 61.60% for the best LLM on that measure, Qwen2.5-72B [S32]. Their task is not ours: localising 23 articles' worth of violations is much broader than "does this call path exist". The honest reading is that AST rules are weak *alone*, and the design only works because the verifier constrains the model rather than replacing it.
- **Two of the three closest open-source repos are stalling, and that is weaker evidence than it first looks.** Fides was archived on 2026-08-28 [S16], three weeks after Ethyca launched a new commercial product [S36], so the archive is evidence about one vendor's open-source strategy rather than about demand. Privado's OSS repo, unpushed since 2025-11-10 [S15], carries the bullet on its own. An empty square in a market can still mean a market that does not pay, and that risk to the "who has this problem" answer belongs in the writeup rather than in a footnote.
- **Nothing here composes with what the user already runs.** Fides consumes YAML datasets [S17], OneTrust and Osano consume connector inventories [S19][S22], Bearer's privacy report defaults to CSV [S3]. We emit Markdown rendered from validated JSON and integrate with none of them. A privacy engineer's honest question — "can this populate my Fides dataset or my OneTrust record?" — currently has the answer "no, you retype it".
