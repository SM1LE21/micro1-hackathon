# 07 — The command line, the terminal output, and the HTML render

`art30` is one command with one subcommand, `argparse`, plain stdout, no colour library and no progress bar. This document fixes the exact lines it prints, because those lines are the demo: the video's middle 90 seconds is a terminal on the left and a rendered record on the right, and the verifier's rejection has to be legible in one frame without narration. It also fixes what happens when there is no terminal, what each stop condition prints, what the HTML page contains, and how a reader walks a JSONL trace by hand.

**Reads with** `docs/spec/00-contract.md` (CLI contract, budgets, trace lines, stop conditions), `docs/spec/04-output-schema.md` (what renders where), `docs/spec/example-record-S10.md` (the document produced by the run mocked below), `.vault/adr/0003-runtime-and-api-decisions.md` (model, replay, no TUI framework), `docs/demo-script.md` (the 90-second segment), `evals/CASES.md` (S10), `docs/writing-rules.md`.

---

## 1. Command surface

```
art30 scan <repo> --arm advanced|baseline [--case ID] [--seed N]
                  [--mode live|replay] [--approve ask|auto] [--out DIR]
```

Exactly the contract's line. Nothing else is added: no `--verbose`, no `--json`, no `--no-color`, no second subcommand. A flag that exists is a flag that needs a test and a sentence in REPRODUCE.md.

| Flag | Default | Meaning |
|---|---|---|
| `<repo>` | required | Path to the repository to read. Read-only; nothing in it is executed (NON-GOALS). |
| `--arm` | required | `advanced` runs verifier and gate; `baseline` runs schema validation only. Same prompt, same tools (ADR 0003 item 4). |
| `--case` | directory basename | Case id for the trace, the results path and the record's provenance. |
| `--seed` | `1` | Harness label only. The model exposes no sampling controls (ADR 0003 item 2); the seed names the run, it does not steer it. |
| `--mode` | `live` | `replay` serves every request from `evals/cache/` and fails on a miss. |
| `--approve` | `ask` | `ask` prompts at the gate; `auto` approves and records `by: "simulated"`. Ignored by `--arm baseline`, which has no gate — including by the TTY check of §7, which runs in the advanced arm only. |
| `--out` | `results/runs/<arm>/<case>/s<seed>` | Where `record.json`, `record.md`, `record.html` are written. |

Environment overrides (`art30/config.py`, all optional): `ART30_MODEL`, `ART30_EFFORT`, `ART30_MAX_TOKENS`, `ART30_TOOL_BUDGET`, `ART30_SUBMIT_BUDGET`. Every one of them is printed in the header line of the run and recorded in `provenance.config` — `max_tokens`, the two budgets, and `overridden`, the names of the variables that were actually set (`04-output-schema.md` §5). A run at non-default settings cannot be mistaken for a reported one, and the artefact can name the settings rather than implying the defaults.

The tool budget is one of them by design. The contract sets 60 tool calls for a synthetic case and 120 for a real one, the CLI has no flag for it, and the harness sets `ART30_TOOL_BUDGET` per run from the case's `source` field in the manifest (`05-eval-harness.md` §5.3). Every R01–R05 run is therefore a run at a non-default budget, which is exactly why the number has to be in the record rather than in a paragraph of REPRODUCE.md.

Makefile targets wrap this and nothing more: `run CASE=S10` is one advanced run at `--approve ask`; `baseline` and `advanced` are three seeds over the dev set at `--approve auto`; `eval` is both arms over all cases; `eval-replay` is the same with `--mode replay`; `report` regenerates tables from `results/`.

## 2. What the output looks like

Five rules, and they hold in every mock below.

1. Phase banners are `[agent]`, `[verify]`, `[gate]`, `[render]` at column 0. Everything else is indented two spaces or more.
2. One line per tool call: a tool-call counter over the tool-call budget, tool name, the arguments that matter, a right-hand result summary, the call's cost and the running total. Lines are appended, never rewritten — no carriage returns, no spinner, so a piped log reads the same as the screen. `steps` on the run's tail line is a different number: it counts model turns (`06-traces.md` §1), and a turn that issues two tool calls prints two lines. The two numbers differ whenever that happens, which is why both are on the tail.
3. A rejection prints one line type per key of the feedback object: the four verifier keys name the store and the claim, then the reason as the verifier wrote it, and the fifth names a JSON path. The CLI prints those strings unchanged, and so does section G of the record.

   | Line | Key | Arms |
   |---|---|---|
   | `REJECT` | `rejected_claims[]` | advanced |
   | `MISSING` | `missing_stores[]` | advanced |
   | `CITE` | `bad_citations[]` | advanced |
   | `UNVERIFIED` | `unverified[]` — store, claim, and the reason the call did not resolve | advanced |
   | `SCHEMA` | `schema_errors[]` — the JSON path, then the message as `format_schema_errors` wrote it (`10-instructions.md` §4.5) | **both** |

   `SCHEMA` is the only rejection channel the baseline has (contract line 95: "Baseline feedback contains only `schema_errors`"), and it carries every I1–I10 failure in both arms, so it is the line most likely to appear on screen in a baseline run. `UNVERIFIED` prints even on an accepted record: `verify/check.py` never blocks on it (`03-verifier.md` §7.1) and `03-verifier.md` §6.1 row 8 makes it routine on a real repository.
4. No colour, anywhere, in either arm. Plain ASCII plus the middle dot in header lines. Nothing to configure, nothing to strip out of a piped log, and the gate block reads the same in a screenshot as in a terminal (`10-instructions.md` §5).
5. The last three lines of any run are the artefact paths, the stop condition with its counters, and cost, wall time and trace path. A person reading only those three lines knows what happened.

## 6. Stop conditions and exit codes

| stop_condition | Exit | Printed |
|---|---|---|
| `accepted` | 0 | the three-line tail above |
| `gate_rejected` | 3 | `[gate] rejected by human. Nothing rendered.` then `gate_rejected · 14 steps · 21 tool calls · 2 submits · record kept at <out>/record.draft.json` |
| `budget_exhausted` | 1 | `[agent] tool-call budget exhausted at 60/60 without submit_record.` then the tail with `budget_exhausted`, and `trace copied to traces/failures/S10-s1.jsonl` |
| `max_submits` | 1 | `[verify] attempt 5 · rejected · no attempts left.` then the tail with `max_submits`, last feedback object echoed in full, trace copied to `traces/failures/` |
| `api_error` | 1 | `[agent] API error after {cfg.max_retries} retries: <type> (request_id <id>).` — interpolated, not spelled, so it cannot drift from `max_retries=4` (`01-architecture.md` §8 and Decision 10). Retries are transport-level only; a 400 is not retried |
| `refusal` | 1 | `[agent] stop_reason refusal at step <n>. Counted as a failure, not re-prompted.` (ADR 0003 item 5) |
| `timeout` | 1 | `[agent] wall-clock timeout at <n>s.` then the tail with `timeout`, trace copied to `traces/failures/`. The harness kills the child at 900 s synthetic / 1800 s real (`05-eval-harness.md` §5.3) |
| `replay_miss` | 4 | `[agent] replay miss: no cached response for request <hash8> at step <n>. The cache is stale or the fixture changed.` stop_condition recorded as `replay_miss`, not `api_error`: a stale cache and a transport failure need different fixes, and folding them together puts `make eval-replay` failures in the same bucket as real API errors in `traces/failures/` |
| `render_failed` | 1 | `[render] citation storage.py:41 no longer contains cleanup_user_files. Nothing written. The record is kept at <out>/record.json.` The trace is copied to `traces/failures/` and the diagnosis names the citation, because a citation that reaches the renderer is one the verifier accepted: this exit is evidence of a verifier bug, not of a bad record |
| usage error | 2 | `argparse` default, plus one line for a semantic error: `--approve ask needs a terminal; use --approve auto` |

Four of the `stop_condition` values in that table — `timeout`, `replay_miss`, `render_failed` and `01-architecture.md` §9's `crashed` — are not in the contract's six-value enum. The exit codes are `art30`'s own and are unaffected; the enum is not, and `06-traces.md` check 14 validates against it after every run. `PROPOSED-CONTRACT-CHANGES.md` P-08 asks for one enum edit covering all four (plus `max_tokens`, which `01` proposal 2 and `02` proposal 1 both ask for). Until it lands the trace records `api_error` with the cause in `run_end.note` and the printed lines and exit codes above are unchanged — which is the reading `01-architecture.md` §9 already takes for a replay miss, and the reason this document's `replay_miss` row and that document's table read differently today.

`art30 scan`'s exit codes are its own and they collide numerically with the harness's (`05-eval-harness.md` §5.5: 2 test split locked, 3 live budget exhausted, 5 replay miss). `evals/harness/run.py` launches `art30` as a child and never propagates a child code unchanged: it maps a child's 4 to its own 5 and every other non-zero child code to a recorded run failure inside a sweep that still exits 0.

On every failure path the trace is flushed and copied into `traces/failures/`, and a `.diagnosis.txt` is written next to it holding one line: the stop condition, the step it happened at, and the last tool call. That file is written by the harness, not by hand, so the "failures are shipped, not hidden" rule cannot rot.

## 7. No terminal

`sys.stdout.isatty()` is checked once at start-up, **in the advanced arm only**.

- Advanced arm, not a TTY, `--approve ask` (a CI job, a Docker run, a pipe): the run stops before the first API call with exit 2 and the message above. Failing before spending money beats failing after.
- Baseline arm: the check does not run and `--approve` is ignored (§1). The flag defaults to `ask`, so a baseline run in a container or through a pipe would otherwise die at start-up over a gate that arm does not have — and the baseline is the arm most likely to be run non-interactively, since it is the comparison a judge reproduces.
- Not a TTY and `--approve auto`: runs normally. Prompts are never printed; the gate block and its banner still are.
- `stdin` closed at the prompt (EOF): treated as `n`, exit 3. Silence is not approval.

## 8. The HTML render

`render/html.py` turns `record.md`'s source data into one self-contained page. Structure, not styling:

- **One template**, one file, no JavaScript, no external stylesheet, no web font, no image. The page opens from a USB stick with no network. Light theme only; there is no dark variant and no toggle, because the page's other output device is a printer.
- **Head**: title `Record of processing — <repository>`, one inline `<style>` block, and a `<meta name="generator">` carrying the run id.
- **Header**: `<h1>`, the provenance table as a two-column `<table>`, and the "technical half of a record / not legal advice" statement in a bordered block that repeats at the top of the print footer.
- **Contents**: a plain `<ol>` of the eight sections, anchors only.
- **Body**: one `<section id="a-inventory">` … `<section id="h-evidence">` per section of 04 §6, in the same order, each with an `<h2>` matching the Markdown heading exactly. Tables carry a `<caption>`.
- **Citations**: every `file:line` renders as `<code class="cite" title="<the cited line, trimmed to 120 characters>">`. That is the hover in the video at 1:15, and it needs no JavaScript. The renderer reads the line from the repository it just scanned — so `render/html.py` takes `record.json` **and** the repository path, not `record.md` alone (proposed contract change 2), and `results/` cannot be re-rendered without the fixture tree in place. If the line no longer contains the cited symbol the render stops with `render_failed` (§6) rather than printing a tooltip that lies.
- **Verdicts**: `<span class="verdict not-reaching">NOT ERASED</span>` or `class="verdict reaching"`. A verdict that does not reach erasure is set in dark red with a rule down the left of its row; everything else is black on white. That is the red row the demo script points at, and it is the only colour on the page. No icons, no badges, no traffic lights, and the row is still legible in greyscale because of the rule.
- **Human cells**: `<span class="empty">requires human completion</span>`, set in the same size as the surrounding text. An empty cell that looks like a placeholder gets skipped; this one is meant to be read.
- **Print**: `@media print` sets A4 margins, breaks before each `<section>`, expands every `title` tooltip into a footnote at the end of its section, and repeats the run id and the not-legal-advice line in the running footer. A judge who prints the page loses nothing.

## 9. The 90 seconds

`docs/demo-script.md` maps onto this output as follows.

| Demo time | On screen | Where it comes from |
|---|---|---|
| 0:00–0:10 | repo tree | `list_tree` output at step 1, or `tree` run by hand before the take |
| 0:10–0:25 | tool calls scrolling, step counter visible | §3 lines 1–13. The counter is in the first column of every line, which is why it is there |
| 0:25–0:40 | the inventory | `record.md` section A, right-hand pane |
| 0:40–1:00 | the rejection | §3 `[verify] attempt 1`. This is the frame the segment exists for: four lines, no colour, the store and the claim on the first line |
| 1:00–1:15 | the gate | §3 `[gate]` block, ending on `> y` |
| 1:15–1:30 | the rendered record, hover on a citation | `record.html`, section D, the `title` attribute of a `<code class="cite">` |

Five corrections the narration needs, each at its timestamp. The cheapest fix for all of them is at the source: `docs/demo-script.md` quotes this document rather than paraphrasing it.

| Time | What the script says | What the product does |
|---|---|---|
| 0:10–0:25 | "Step counter visible top right" | The counter is in the first column, on the left (§2 rule 2, decision 4) |
| 0:25–0:40 | "Twelve fields, six stores" | S10 has eleven fields and four stores (`example-record-S10.md`) |
| 0:25–0:40 | the `notes` column with the comment about phone numbers | That is case S07, not S10 |
| 0:40–1:00 | `REJECT store=uploads claim=erased reason=no path close_account → storage.delete; helper cleanup_user_files defined at storage.py:41, never called` | The verifier's actual string is `REJECT   uploads · erasure.verdict=erased` with the reason on continuation lines (§3). §2 rule 3 says the CLI prints the verifier's strings unchanged, so the beat the segment exists for would show a sentence that is not on screen |
| 1:15–1:30 | "Here it takes forty seconds" | The run tail reads `209s`. Either say "three and a half minutes" or cut the number: the comparison the line is making is with hand-labelling minutes, and a wrong number spoken over a visible one is worse than none |

Either the narration is recorded against S10's real counts, or the segment uses S07 for 0:25–0:40 and says so. Growing the S10 fixture to fit a voice-over would change a test-split case, which is the one thing that must not happen for the sake of a video.

## 10. `traces/README.md`

The file's content, to be copied verbatim when the traces directory is populated:

````markdown
# Traces

`traces/<arm>/<case>-s<seed>.jsonl` — one runtime trace per run, one JSON object per line.
`traces/failures/` — the same files for runs that failed, each with a `.diagnosis.txt` beside it.
`traces/build-trajectory.html` — the coding-agent sessions that built this repository, rendered
by `make traces` (author-only target; the HTML is committed so no judge needs to run it).

## Line types

| `type` | When | Fields that matter |
|---|---|---|
| `run_start` | once, first line | `run_id`, `arm`, `case`, `seed`, `model`, `effort`, `mode` |
| `step` | one per model turn | `step`, `phase`, `reasoning`, `text`, `tool_calls[]`, `tool_results[]`, `usage`, `cost_usd`, `cost_cum_usd` |
| `checkpoint` | at the human gate | `risk`, `summary`, `decision`, `by`, `wait_s` |
| `run_end` | once, last line | `stop_condition`, `steps`, `tool_calls_total`, `submits`, `verify_rounds`, `wall_s`, `cost_usd` |

`reasoning` is the model's summarised thinking, not raw chain of thought. Tool outputs are stored in full.

## Reading one by hand

Everything below is stdlib Python; no `jq`, no viewer.

```
# the shape of the run
python -c "import json,sys;[print(json.loads(l)['type']) for l in open(sys.argv[1])]" traces/advanced/S10-s1.jsonl

# one line, pretty
python -c "import json,sys;print(json.dumps(json.loads(open(sys.argv[1]).readlines()[int(sys.argv[2])]),indent=2))" traces/advanced/S10-s1.jsonl 14

# every tool call in order
python -c "
import json,sys
for l in open(sys.argv[1]):
    d=json.loads(l)
    for c in d.get('tool_calls',[]): print(d['step'], c['name'], c['input'])
" traces/advanced/S10-s1.jsonl
```

A tool call and its result are linked by id within one line: `tool_calls[].id` matches `tool_results[].call_id`
on the same step. Follow that pair to see exactly what the model was shown. The only unpaired call is the
last one of a run that did not end `accepted`.

Three places worth going first:

1. The last `submit_record` call — `input.record` is the record that was accepted.
2. The `step` lines with `phase: "verify"` — the feedback objects, in order. `rejected_claims[].reason`
   is the sentence the verifier wrote; it appears unchanged in the record's section G.
3. The `checkpoint` line — the risk rating, what the human was asked, and whether `by` is `human` or
   `simulated`.

Cost: `cost_usd` per step, `cost_cum_usd` running, both computed from `usage` at list prices
(input $5/MTok, output $25/MTok, cache write ×1.25, cache read ×0.1).

## There is no trace viewer

Reading a trace means reading JSON with the three commands above. Nothing in this repository renders
runtime traces into a page: a viewer would be a second product to build, test and reproduce, and the
one rendered artefact a reader needs — the build trajectory — is committed as HTML already.
````

## 11. What is not built

No trace viewer, no TUI, no `--watch`, no web UI, no `art30 render` subcommand for re-rendering an existing `record.json`, no `--format json` on the CLI (the JSON is a file, not a stream). Each of these is half a day and none of them moves a rubric line.

---

## Decisions taken here

1. The CLI is the contract's line and nothing more. Flags that are not in `00-contract.md` are not added.
2. Output is append-only plain text: no carriage returns, no spinner, so the screen, a pipe and a log file are the same bytes.
3. No colour anywhere, so there is nothing to disable off-TTY and nothing to strip from a log.
4. One line per tool call, carrying the tool-call counter over the tool-call budget, arguments, result summary, that call's cost and the running cost. The counter is in column one because the video needs it visible while lines scroll. `steps` on the tail is model turns and is a different number; both are printed.
5. The gate prints its banner in `--approve auto` too, and records the decision in the trace either way.
6. Recipient kinds are collected at the gate with a one-key prompt per third-party store, in `ask` mode on a TTY only. Unanswered stays `unknown`.
7. Non-TTY plus `--approve ask` fails at start-up with exit 2, before the first API call. EOF at the prompt counts as `n`.
8. Exit codes: 0 accepted, 1 run failure, 2 usage, 3 gate rejected, 4 replay cache miss. They are `art30`'s own; `evals/harness/run.py` maps a child's 4 to its own 5 and propagates nothing unchanged.
9. On a rejected gate the submitted record is kept as `record.draft.json` — the name `05-eval-harness.md` §4.2 and §6 read, and the file `false_safe_in_draft` and `f1_draft` are computed from — and no Markdown or HTML is written. It is a draft, not a verdict: the run's own `f1`, `pass` and `false_safe` stay zero, false and zero, and the draft's numbers are reported beside them so the gate cannot launder a false safe out of the headline row.
10. The HTML render is one self-contained light-theme file with no JavaScript; citation hovers are `title` attributes, so `render/html.py` reads `record.json` and the repository, and it stops with `render_failed` rather than emit a tooltip whose line no longer holds the cited symbol.
11. No trace viewer. `traces/README.md` teaches three stdlib commands instead, and the only rendered trajectory in the repository is the committed build-trajectory HTML.
12. The gate's own text belongs to `10-instructions.md` §5; this document owns the `[gate]` banner, the recipient prompt's placement, and everything printed before and after the block. Two documents describing one screen is the risk; one of them printing the string is the fix.
13. The demo narration is corrected to S10's real counts rather than the fixture being grown to fit the narration — five corrections, listed with their timestamps in §9, and `docs/demo-script.md` quotes §3 for the rejection rather than paraphrasing it.
14. Every key of the feedback object has a printed line type. `SCHEMA` prints in both arms and is the baseline's only rejection channel; §5b shows a baseline rejection so the arm is not represented by its happy path alone.
15. Every counter printed in this document comes from the one invented run in `06-traces.md` §2, the `gate_rejected` row of §6 included — it was the one exception and now reads 14 steps, 21 tool calls, 2 submits. Five documents describe that run (`02-agent-loop.md` §9, `04-output-schema.md` §5, `06-traces.md` §2, `example-record-S10.md` and this one) and they are refreshed together, from the first real trace, in one commit.
16. Every environment override is recorded in `provenance.config`, tool budget included, because the 60/120 split makes every real-repo run a non-default run.

## Open risks

- **The mock is a promise.** Every number in §3 (21 tool calls, 14 steps, 1 verify round, $0.41, 209 s) is invented ahead of the first run, and it is now invented in four places that have been made to agree rather than one. If the real run needs 30 tool calls or two more verify rounds, this document is updated from the trace and the video is cut against the real one. The shape of the lines is the commitment; the counts are not.
- **The gate as a demo prop.** The recipient-kind prompt adds a second interaction to a checkpoint the contract describes as a single decision. It is defensible — the contract says the human sets that cell at the gate — but it lengthens the moment the video has fifteen seconds for. If it does not fit, the prompt moves behind a `--set-recipient-kinds` flag and the cells stay `unknown`.
- **Tooltip fidelity.** Embedding the cited source line in a `title` attribute puts fixture source into the HTML. For synthetic repositories that is fine. For a vendored real repository it copies a few lines of licensed code into the artefact; the LICENSE travels with the fixture, and the render is not published, but it is worth knowing before R01–R05 are rendered.
- **`traces/README.md` — ownership settled.** `06-traces.md` now exists and owns the trace contract, the worked run and the validator. §10 keeps only the reader-facing file that ships in `traces/`, and every rule in it is a restatement of `06-traces.md` §1 and §3; where they disagree, that document wins. The residual risk is drift between a restatement and its source, which is why §10's text is short and points at the validator's checks rather than repeating them.
- **`render_failed` fires after the human has approved.** A citation that no longer resolves is caught in phase 4, past the gate, so the run ends with an approved record and no rendered artefact. That is the right order — a tooltip that lies is worse than a missing page, and `record.json` is kept — but it means the one stop condition a person has already signed off on is the one they cannot act on without the author. It should be rare by construction: the verifier's citation check ran over the same lines in phase 2.
- **The demo script is a second document about this screen.** §9 lists five corrections it needs today. It is not this document's file, so the list can only go stale in one direction: if `docs/demo-script.md` is fixed at the source, §9 shrinks to a pointer.
- **One screen, two owners.** The gate block is specified here and in `10-instructions.md` §5. They agree today because this document was reconciled to that one after both were drafted; they will drift the first time either is edited alone. The code should hold the template in exactly one module (`advanced/arm.py`) and this document should quote it, not restate it.
- **Cost lines in the header.** Printing per-step cost on screen is honest and slightly hostile to a viewer watching a live run climb. It stays: turns and tool calls are reported metrics, not hidden costs.

## Proposed contract changes

**1. Contract §Trace contract, the `checkpoint` line.** Add one optional field:

```
{"type":"checkpoint", "tool":"request_approval", "caller":"harness", "risk":"low|medium|high",
 "summary", "decision":"approved|rejected", "by":"human|simulated", "ts",
 "human_completions": {"recipient_kind": {"stripe": "processor"}}}
```

Reason: the contract says the human sets `recipient_kind` at the gate, and the trace as specified has nowhere to record what the human typed. Without it, `record.json` would carry a value with no audit trail — the one thing this project refuses everywhere else. The field is omitted when the human set nothing, so existing lines stay valid.

**2. Contract §Repository layout, `render/html.py`.** The layout reads `render/html.py  record.md → record.html (single template, no JS)`.

Proposed wording: `render/html.py  record.json + repo path → record.html (single template, no JS)`.

Reason: the citation tooltips carry the cited source line, and only the repository holds it. An engineer building from the contract writes a Markdown-to-HTML function and §8's requirement is invisible to them. The consequence is worth stating in the same line: a `results/` directory cannot be re-rendered without the fixture tree in place.

**3. Contract §Trace contract, risk rating.** The rating reads: "`high` if any store is `not_erased`, `pseudonymised`, `external_manual`, `no_schedule_evidenced` or `unverified` with an `identifier` or `contact` field; `medium` if every store reaches erasure but at least one only after a timer; `low` otherwise."

Proposed wording: add `no_entry_point` to the `high` list, so it reads "`high` if any store is `not_erased`, `pseudonymised`, `external_manual`, `no_entry_point`, `no_schedule_evidenced` or `unverified` with an `identifier` or `contact` field".

Reason: a repository where every store is `no_entry_point` matches neither the `high` list nor the `medium` clause, so it falls to `low` — and `10-instructions.md` §5 renders `low` as "every store reaches erasure directly", which is the opposite of the finding. S08 and R04 are the two cases built to test whether the tool can say there is no way to delete a user, and as specified their gate screens would tell the approver the opposite, at the lowest urgency, directly above "You are approving a document you will sign". A human-oversight control that inverts under the condition it exists for fails PDF ground rule 05.

Two sibling edits follow from it and belong to their own documents: `10-instructions.md` §5 re-words `low` to "every store reaches erasure directly and an entry point was found" and gains a fourth `risk_reason` shape, "no account-deletion path was found in this repository; no store reaches erasure"; `03-verifier.md` §6.4 adds `no_entry_point` to the flag list it returns for the rating.

**4. Contract §Trace contract, the `stop_condition` enum.** `06-traces.md` §Proposed contract changes 2 already asks for `timeout`. Two more values belong in the same edit: `replay_miss` and `render_failed`.

Reason: both are recorded today as something they are not. A replay miss folded into `api_error` puts `make eval-replay` failures in the same bucket as transport failures in `traces/failures/` and in the `success + failure == n` breakdown, and ADR 0003 item 6 wants that failure loud and distinct. A render that stops on a citation the verifier accepted has no stop condition at all as the contract stands, so the one exit that points at a verifier bug would be indistinguishable from a crash. `06-traces.md` check 14 validates the enum, so the three values travel together.
